OPENPORT TEST TABLE V1 — instrument-cluster testing and CAN commands
English interface and guide — 22 October 2026

STARTUP AND WIRING
1. Build OPENPORT_TEST_TABLE.exe as described in README.md.
2. Close ODIS, VCDS, VCP and other applications using OpenPort.
3. Connect OpenPort CAN-H to the instrument cluster CAN-H wire, and CAN-L
   to CAN-L. Use the correct pinout and power supply for your bench setup.
   USB connection to the computer alone is not sufficient.
4. Run OPENPORT_TEST_TABLE.exe or POKRENI.bat.
5. Select the correct bitrate and identifier mode, then click CONNECT.
   The original bench profile uses 500000 bit/s and 11-bit identifiers.
   These settings are not universal for every cluster or CAN network.

The executable is Windows x86 and also runs on 64-bit Windows with an
installed x86 J2534 OpenPort driver. The executable does not require Python,
PowerShell or .NET. Python is needed only for the supplied Linux build scripts.
The application locates OpenPort through the J2534 registry. You can edit the
DLL path before connecting. A common path is:
  C:\Windows\SysWOW64\op20pt32.dll
The repository does not include the Tactrix driver.

MANUAL COMMANDS
- CAN ID is hexadecimal, for example 5C1 or 0x5C1.
- Data contains hexadecimal byte pairs: 00 00 00 60 or 00000060.
- Classic CAN supports 0 to 8 payload bytes. CAN FD is not supported.
- SEND ONCE sends a single frame.
- REPEAT sends frames at an interval from 20 to 60000 ms.
- Repeats is the total number of frames; 0 means continue until STOP.
- Enter CAN bitrate in bit/s, for example 500000, 100000 or 125000.
- Select 29-bit mode before connecting. Disconnect before changing it.

This is a RAW CAN tool. It sends the bytes entered by the operator.
It does not automatically assemble ISO-TP, VW TP2.0, KWP/UDS sessions or
long BAP/DDP packets. Those protocols require correctly prepared CAN frames,
including their headers, sequence numbers and acknowledgements as applicable.
A CAN ID is not a diagnostic address. Universal gauge, fuel-level and warning
lamp commands are not included.

COMMAND SEQUENCES
Each line uses this format:
  CAN_ID#HEX_DATA@DELAY_AFTER_FRAME_MS

Example: OK button press, followed by release, for the original bench profile:
  5C1#28 00 00 60@100
  5C1#28 00 00 60@100
  5C1#00 00 00 60@100
  5C1#00 00 00 60@200

The first frame is sent immediately. The value after @ is the delay after that
frame, before the next line or cycle. There is no extra wait after the last
frame of the final cycle. Cycles = 0 means continuous operation.
Blank lines and comments starting with ; or // are allowed.
A sequence may contain up to 128 commands. The entire sequence is validated
before any frame is sent. Timing depends on Windows and the driver; this is
not a precision timing generator.
SAVE and LOAD use SEKVENCA.txt beside the executable. Loading does not send
commands. Use ASCII text; UTF-8 with or without a BOM is supported when the
contents are ASCII. Avoid non-ASCII characters in sequence comments.

STEERING / CLUSTER MENU BUTTONS
The included profile comes from the original working bench setup:
  UP      5C1 / 22 00 00 60
  DOWN    5C1 / 23 00 00 60
  LEFT    5C1 / 09 00 00 60
  RIGHT   5C1 / 0A 00 00 60
  OK      5C1 / 28 00 00 60
  BACK    5C1 / 29 00 00 60
  RELEASE       00 00 00 60

These payloads are specific to that profile, not universal vehicle commands.
A normal click lasts 200 ms; long-press buttons last 2 seconds. The frame
period is 100 ms, with 200 ms of released state between clicks. After the
first click, neutral frames continue every 100 ms until STOP.
Steering buttons work in 11-bit mode. Manual sending and sequences replace
an active steering profile; a steering click stops active manual repetition
or a sequence.

STOP AND BACKGROUND OPERATION
STOP ALL or Escape stops repetition, sequences and the steering profile.
If this tool was sending a recognized 5C1 button press, it also attempts to
send a release frame. STOP keeps the CAN connection and RX recording active.
DISCONNECT and closing the window stop sending and close OpenPort.
By default, transmission stops when the window loses focus. Enable
Keep sending in background if transmission must continue in another window.
A TX, RX or recording error stops sending and closes the connection.
After a driver error, you can reconnect. If recording fails, move the tool
to a writable folder.

DISPLAY AND LOGS
The monitor shows the last 96 visible RX/TX events.
The ID filter affects only the display: for example 5C1,6C8,6DF or * for all.
Pause display and CLEAR DISPLAY do not interrupt CSV recording.
LOG_TEST_TABLE_*.txt contains the driver path, versions, actions and errors.
LOG_TEST_TABLE_*.csv contains received frames for the selected identifier mode,
TX_REQUEST, TX_ACCEPTED, TX_FAILED and adapter status events.
TX_ACCEPTED means driver acceptance, not proof of a cluster response.
Adapter TX echoes are separated from RX responses. RX data loss is marked.

VERIFICATION
Build checks cover PE32 structure, x86 ABI, imports, relocation values and ASLR.
The native test suite uses mocked Win32/J2534 functions to exercise parsing,
CAN ID/DLC limits, sequences, repetition, STOP/release, background operation,
29-bit flags, RX/echo handling, driver errors and reconnection. ASan/UBSan
checks and 30000 randomized parser inputs are included.

On 22 October 2026, the maintainer reported that the original version worked
on his physical OpenPort setup. This English interface revision has passed
software verification; it has not received a separate physical-device test.
Hardware compatibility beyond the reported setup is not established.
